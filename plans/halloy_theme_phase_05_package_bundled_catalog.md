# Halloy Theme Phase 05 — Package the Bundled Halloy Catalog

> **Plan status: HISTORICAL — shipped.** The outcome is documented in [architecture/core/themes.md](../architecture/core/themes.md); this file is the historical record.

## Objective

Convert the checked-in top-level Halloy theme collection into reliable Python package resources and prove that bundled theme discovery/loading works from release artifacts rather than only from a source checkout.

This phase connects Phase 04's registry to real packaged resources. It must preserve external-theme customization as a separate runtime path.

## Dependencies

Requires:

- Phase 01's approved catalog and resource-layout decision;
- Phase 02 parser;
- Phase 03 translator;
- Phase 04 registry/resource abstractions.

## Required implementation work

### 1. Establish the canonical bundled resource directory

Create the package-owned resource path selected in Phase 01, expected to resemble:

```text
app/themes/bundled/
  *.toml
```

Add `__init__.py` only where required for package/resource semantics. Theme files are data, not executable Python modules.

Decide and document the role of the existing top-level `themes/` directory. Preferred options, in order:

1. retain it as the canonical source catalog and add a deterministic sync/check mechanism to package resources;
2. move the canonical files into the package and retain a documented sample/external directory at the root;
3. generate package resources during the build only if this remains transparent and reproducible.

Avoid two silently divergent copies. If both locations remain checked in, CI must verify exact catalog and content equality.

### 2. Curate and copy the approved catalog

Use Phase 01 inventory findings. Include every theme that:

- parses under Phase 02;
- translates under Phase 03;
- has acceptable redistribution provenance;
- is not a duplicate or explicitly excluded legacy artifact.

Any exclusion must be committed in a manifest with a reason. Do not silently omit a failing file.

Preserve filenames where possible because external overrides depend on stable names.

### 3. Add attribution and licensing material

Document that the themes use the Halloy-compatible format and identify their upstream source. Preserve or include required license and attribution text.

Add a machine-readable or human-readable catalog manifest containing at least:

- theme name;
- source filename;
- bundled status;
- upstream attribution where known;
- optional light/dark classification generated by tests, not manually trusted.

Do not imply that Halloy itself endorses this project.

### 4. Update Python packaging metadata

Inspect the actual packaging stack and update the appropriate files, which may include:

- `pyproject.toml` package-data configuration;
- `MANIFEST.in`;
- setuptools include-package-data settings;
- source distribution configuration;
- any custom release scripts.

Requirements:

- wheels include every approved `.toml` resource;
- source distributions include the same catalog;
- editable installs behave consistently;
- the registry uses `importlib.resources` and not `cwd`-relative paths.

Avoid broad wildcard inclusion of unrelated files.

### 5. Update container and deployment packaging

Inspect Dockerfiles, `.dockerignore`, compose files, and install scripts.

Ensure:

- the application image receives packaged themes through normal package/application installation;
- no runtime bind mount is required for bundled themes;
- an optional external theme directory can still be mounted/configured separately;
- read-only application filesystems remain compatible;
- external customization is not written into package resources.

Document a recommended container path for external themes, such as `/app/data/themes`, consistent with existing data-volume conventions.

### 6. Add build-artifact verification

Add a release-oriented test or script that:

1. builds a wheel;
2. installs it into an isolated environment or inspects it reliably;
3. imports the application theme package;
4. lists bundled themes through the Phase 04 registry;
5. loads and translates at least one dark and one light theme;
6. verifies the expected catalog count or manifest set;
7. runs outside the repository root to catch accidental relative-path dependencies.

Also inspect the source distribution if the project publishes one.

The test should fail when a new top-level approved theme is not synchronized into package resources.

### 7. Add resource integrity tests

For every packaged resource:

- filename is safe and unique;
- resource size is within limits;
- parser succeeds;
- translator succeeds;
- generated CSS is complete;
- manifest entry exists;
- source/bundled content matches when dual copies are retained.

Compute hashes if useful for deterministic equality and cache identity.

### 8. Preserve external override semantics

Add an integration test using the installed/bundled resource path plus a temporary external directory:

- bundled theme is listed;
- a novel external theme extends the list;
- a same-name external file overrides the bundled file;
- removing/invalidation restores the bundled version;
- no code writes to bundled resources.

### 9. Update operator-facing configuration examples

Add commented configuration showing:

```toml
[themes]
external_dir = ""
```

Clarify that bundled themes require no configuration and that external themes are optional. Do not yet expose final admin or database settings planned for later phases unless the configuration parser already needs the directory path for tests.

## Files expected to change

Likely:

- `app/themes/bundled/*.toml`;
- `app/themes/bundled/__init__.py` if needed;
- theme manifest/attribution files;
- `pyproject.toml` and/or `MANIFEST.in`;
- Docker/deployment files where necessary;
- configuration examples;
- packaging and registry integration tests;
- CI/release workflow files if artifact verification belongs there.

## Testing requirements

Run:

- catalog-wide parser and translation tests;
- package-resource listing tests;
- wheel build/install smoke test;
- source distribution content check where applicable;
- container build or artifact inspection relevant to repository CI;
- bundled plus external override integration test;
- full existing lint/type/test suite.

The wheel smoke test must not pass merely because the source checkout is importable. Use an isolated path/environment or direct wheel-content verification plus isolated import.

## Acceptance criteria

- Every approved Halloy theme is present in package resources.
- Wheels and source distributions include the expected catalog.
- Registry discovery works from installed artifacts outside the repository root.
- At least one dark and one light bundled theme load and translate in artifact tests.
- Container/release packaging does not require the root `themes/` directory at runtime.
- External theme directories still extend and override the installed bundled catalog.
- Source and packaged catalogs cannot silently diverge.
- Attribution and licensing requirements are documented and shipped.
- Existing application rendering behavior remains unchanged until the later integration phase.

## Non-goals

- database migration from `theme_preset`;
- Jinja/runtime replacement of `THEME_PRESETS`;
- visitor dark/light rewrite;
- admin theme preview;
- broad CSS token cleanup.

## Handoff notes

After this phase, the parser, translator, registry, and package resources should form a complete backend subsystem that can be integrated without further filesystem design. The next plan should focus on configuration/persistence migration and must not reintroduce repository-relative bundled theme lookup.
