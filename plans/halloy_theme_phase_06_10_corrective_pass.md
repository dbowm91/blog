# Halloy Theme Phase 06–10 Corrective Pass

## Objective

Close the remaining correctness and lifecycle gaps in the persisted theme configuration, runtime service, visitor color-scheme behavior, and admin endpoints before moving into operator tooling and release hardening.

This pass is intentionally narrow. It must not redesign the Halloy parser, translation model, registry precedence, or CSS token contract.

## Findings to address

1. `theme_default_scheme` is persisted but first-time visitors always default to `system`.
2. Crafted invalid theme names can raise `ThemeValidationError` through admin save/preview endpoints and produce avoidable 500 responses.
3. Legacy preset migration does not explicitly preserve the old light/dark visual mode.
4. The process-global theme service is difficult to reconfigure across multiple Flask app instances and tests.
5. The legacy `THEME_PRESETS` fallback remains in the context processor and should be clearly bounded until final removal.
6. CI artifact verification and the full Halloy test matrix need an explicit closure gate.

## Workstream A — Apply the persisted default scheme

Expose the effective server default to the document before the bootstrap executes. Preferred options:

- an escaped inline constant generated by Jinja;
- a `data-default-color-scheme` attribute on `<html>`;
- a small JSON configuration block with a CSP nonce.

The bootstrap contract must be:

1. use a valid stored visitor preference when present;
2. otherwise use the persisted/configured site default;
3. resolve `system` against `prefers-color-scheme`;
4. set `data-color-scheme` before deferred styles load.

Update `color-scheme.js` to use the same default contract. Avoid duplicating divergent validation logic between bootstrap and module code.

Tests:

- no storage + site default dark → dark before first paint;
- no storage + site default light → light before first paint;
- no storage + site default system → OS preference;
- stored visitor value overrides site default;
- invalid storage falls back to site default;
- unavailable local storage still honors site default.

## Workstream B — Normalize admin validation errors

Wrap all admin registry resolution and loading entry points with explicit handling for:

- `ThemeValidationError`;
- `ThemeNotFoundError`;
- `ThemeParseFailure`;
- `ThemeLoadError`.

Expected behavior:

- settings save: flash a field-specific validation error and redirect;
- preview: return structured JSON with HTTP 400;
- refresh: log operator-useful detail, return a safe flash message;
- no traceback or absolute path in responses.

Avoid broad `except Exception` where a typed registry error is expected. Retain a final defensive catch only around the complete refresh operation.

Add tests using traversal strings, control characters, overlong names, malformed external overrides, and missing themes.

## Workstream C — Decide migration preservation semantics

Adopt and document one explicit migration rule.

Recommended rule:

- `github-dark`, `solarized-dark`, `monokai` → mapped dark theme and `theme_default_scheme='dark'`;
- `github-light` → mapped light theme and `theme_default_scheme='light'`;
- unknown/empty preset → configured defaults and `system`.

Update the Alembic migration only if it has not shipped in an immutable release. If it may already be deployed, add a follow-up data migration rather than rewriting history.

Tests must cover upgrade and downgrade behavior on SQLite and the project's supported production database.

## Workstream D — Scope the theme service to the Flask app

Replace or wrap the module-global singleton with app-owned state:

```python
app.extensions["theme_service"] = ThemeService(...)
```

Requirements:

- each app instance receives its own configured defaults and external directory;
- tests can create multiple apps without cross-contamination;
- background and request code can retrieve the active service safely;
- app factory remains the only normal initialization path;
- no database access occurs during module import.

A compatibility accessor may remain, but it should resolve through `current_app` and fail clearly outside an application context unless an explicit service is supplied.

## Workstream E — Bound the legacy fallback

Keep the old `THEME_PRESETS` fallback only as a temporary emergency boundary if required. Add a clear comment and test proving it is used only when the Halloy service cannot initialize.

Do not let legacy cached settings become the normal database fallback. Prefer the Halloy emergency `BlogTheme` path when the database is unavailable.

Record final deletion in Phase 15.

## Workstream F — CI closure

Ensure CI explicitly runs:

- Ruff;
- mypy;
- unit/integration tests;
- coverage threshold;
- Halloy catalog parse/translate tests;
- wheel and sdist build;
- isolated artifact verification;
- migration tests;
- browser/E2E color-scheme tests where supported.

Do not rely on test discovery alone for artifact verification; add a named CI step.

## Expected files

Likely changes:

- `app/templates/base.html` and admin base templates;
- `app/static/js/shared/color-scheme.js`;
- `app/routes/admin/settings.py`;
- `app/themes/service.py`;
- `app/__init__.py`;
- migration files or a follow-up migration;
- context processor fallback path;
- CI workflows;
- Phase 06–10 tests and documentation.

## Acceptance criteria

- persisted default scheme affects first-time visitors;
- stored visitor preference retains precedence;
- invalid theme names never create an admin 500;
- legacy migrations preserve intended visual mode according to documented policy;
- multiple Flask app instances use isolated theme services;
- normal rendering no longer depends on `THEME_PRESETS`;
- wheel/sdist and complete Halloy validation are explicit CI gates;
- full test, lint, type, migration, and artifact suites pass.

## Non-goals

- new CLI commands;
- new accessibility policy;
- cache architecture redesign;
- removal of every legacy symbol;
- new theme format features.
